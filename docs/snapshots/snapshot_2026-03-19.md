## 2) System Architecture View
תזרים נתונים (נכון ל-Phase 0):

- Upload PDF → Parse (FastAPI + PyMuPDF) → Segment (naive blank-line split) → Layer 1 Classify Pending → Layer 2 DSPy Risk Pending → Layer 3 Hybrid Score Pending → Store DB Not implemented → UI rendering (`parsed_clauses`)
- **Frontend (Next.js):** משתמש מעלה `PDF` (multipart/form-data) באמצעות `UploadDropzone`
  - ה-UI שומר מצבי `idle/loading/success/error`
  - לאחר הצלחה הוא מציג את `parsed_clauses` ככרטיסיות
- **Backend (FastAPI):** מקבל את הקובץ ב-Endpoint יחיד:
  - `POST /api/contracts/upload`
  - קורא bytes מה-PDF
  - מחלץ טקסט באמצעות **PyMuPDF** (`fitz`)
  - מבצע **naive segmentation** (פיצול לפי רווחים לבנים)
  - מחזיר **JSON envelope** זהה תמיד
- **ML/DSPy/Hybrid scoring:** כרגע **Pending** (לא ממומש בקוד בפועל)
  - במקום זאת, segmentation נאיבי מתפקד כ”Placeholder” לשכבת קלאוזים

גבולות ארכיטקטורה:
- `frontend/` שולח בקשה ל-`backend/main.py` (אין API routes בתוך Next שמחליפים את FastAPI).
- `backend/` מחזיק רק את שלב ה-parsing וה-segmentation הבסיסי.

## 4) Core Achievements (Technical)

1. **Backend Endpoint יוצר חוזה JSON אחיד**
   - **מה השתנה:** מימוש Endpoint `POST /api/contracts/upload` שמחזיר:
     - הצלחה: `status="success"`, `filename`, ו-`parsed_clauses[]` עם `clause_index` ו-`raw_text`
     - כשל: `status="error"`, `parsed_clauses: []`, ו-`detail`
   - **למה:** כדי שה-Frontend/Dev2 יוכלו להסתמך על schema קשיח ללא קשר לפיתוחים עתידיים (DB/ML).
   - **איפה בקוד:** `backend/main.py → @app.post("/api/contracts/upload")` (`upload_contract`)
   - **השפעה/סיכונים:**
     - אין עדיין ולידציית `max file size` בקוד (רק בדיקת סוג/שם קובץ כ-PDF).
     - segmentation נאיבי עשוי לייצר `0` סעיפים אם ל-PDF אין טקסט חלוץ.

2. **FastAPI startup crash (response model type) טופל**
   - **מה השתנה:** הוגדר return type פשוט (`dict[str, Any]`) והוסרה חתימה בעייתית שהייתה עלולה לגרום ל-FastAPIError בזמן בניית response field.
   - **למה:** להבטיח ש-Uvicorn עולה יציב ב-Start-up כדי ש-Frontend לא ייתקל ב-500/connection errors.
   - **איפה בקוד:** `backend/main.py`
     - `upload_contract(...)-> dict[str, Any]`
     - `@app.exception_handler(HTTPException)` שמייצר תמיד מעטפת error לפי החוזה.
   - **השפעה/סיכונים:**
     - ה-handler קורא `HTTPException.detail` כ-dict במקרים שבהם `detail` הוא `{filename, message}`; אחרת הוא ממיר למחרוזת.
     - חשוב לשמור על תצורת `detail` כאשר מוסיפים ולידציות נוספות בעתיד כדי לא לשבור את מעטפת ה-error.

3. **PyMuPDF extraction + naive segmentation יושמו כ-base heuristics**
   - **מה השתנה:**
     - PyMuPDF מחלץ טקסט לכל עמוד (`page.get_text("text")`)
     - הטקסט נאסף עם `"\n\n".join(page_texts)` ואז מבוצע פיצול:
       - `re.split(r"\n\s*\n", full_text)`
     - כל segment לא-ריק הופך clause עם:
       - `clause_index` **1-based** ורציף
       - `raw_text` לאחר `strip()`
   - **למה:** כדי לתת output קריא ל-UI כבר ב-Phase 0, לפני הכנסת spaCy/sklearn/DSPy.
   - **איפה בקוד:** `backend/main.py → upload_contract`
     - extracción: `fitz.open(stream=raw_bytes, filetype="pdf")` + `page.get_text(...)`
     - segmentation: `re.split(r"\n\s*\n", full_text)`
   - **השפעה/סיכונים:**
     - Heuristic “חספסני” עלול להתנהג שונה בין סוגי PDFs (מוטבע טקסט מול סריקה, מבנה רשימות וכו’).

4. **Frontend “Walking Skeleton UI” + state management + rendering**

## 5) API Contracts & DB Schema (Crucial for Dev1 ↔ Dev2 Sync)

### 5.1 Strict API Contract: `POST /api/contracts/upload`

**Request**
- `Content-Type: multipart/form-data`
- field name: **`file`** (בדיוק)

- **Max file size (10MB):** כרגע **אין אכיפה בקוד**.
  - ב-UI: `UploadDropzone.tsx` בודק רק PDF לפי `type`/סיומת שם הקובץ (אין check על bytes).
  - ב-Backend: אין בדיקת bytes מול 10MB לפני parsing.
- **CORS (קריטי ל-local dev):**
  - מאופשר ב-`backend/main.py` עבור `http://localhost:3000` ו-`http://127.0.0.1:3000`.

**Response — Success (`200`)**
```json
{
  "status": "success",
  "filename": "string",
  "parsed_clauses": [
    {
      "clause_index": 1,
      "raw_text": "string"
    }
  ]
}
```

**Response — Error (`400` במימוש הנוכחי; מטופל ע"י exception handler)**
```json
{
  "status": "error",
  "filename": "string",
  "parsed_clauses": [],
  "detail": "string"
}
```

כללים קשיחים (חייבים להישמר גם אחרי שמכניסים spaCy/sklearn/DSPy/DB):
- `parsed_clauses` **חייב להתקיים תמיד**.
- במקרה error: `parsed_clauses` חייב להיות `[]`.
- `clause_index`:
  - חייב להיות **מספר שלם**
  - **1-based**
  - מונוטוני ורציף ביחס לסדר סעיפים שנוצר
- `raw_text` הוא string טקסט הסעיף/הקטע.

### 5.2 DB Schema
**כרגע אין DB/ORM ממומש בקוד.**

סימנים בקוד:
- אין ספריות/מודולים תחת `backend/` עבור `database/`, `ml/`, או `dspy/` (בפועל בקוד קיים רק `backend/main.py` + `backend/requirements.txt` + README).
- `frontend/package.json` ו-`backend/requirements.txt` לא כוללים תלותי ORM/DB (למשל `sqlalchemy`, `psycopg2`, וכו’) ולא כוללים תלותי spaCy/sklearn/DSPy.

עם זאת, ה-DB schema המתוכנן נמצא ב-`PRD/DataModel.md` (למשל `contracts`, `parsed_clauses`, ורכיבי risk/plain-language), אך הוא **לא** ממומש בריצה הנוכחית של Phase 0.

## 7) UPL Compliance Audit (Unauthorized Practice of Law)

מה הקוד עושה בפועל (בהיבט UPL):
- ה-backend מחלץ טקסט ומחזיר אותו כ-`raw_text` ללא יצירת ייעוץ משפטי או ניסוח המלצות.
- ה-frontend מציג את ה-`raw_text` כמו שהוא (ללא “מסקנות”, “המלצות”, או ניסוח אופרטיבי).

בדיקות “ימצא disclaimer/prompt constraints” בקוד הנוכחי:
- לא נמצא בקוד UI טקסט disclaimer ייעודי (לפי סריקת מחרוזות “disclaimer/UPL/legal advice” ב-`frontend/src`).
- אין DSPy, ולכן אין prompt constraints ב-DSPy במימוש הנוכחי.

משמעות:
- **הסיכון המשפטי בפועל כרגע נמוך יותר**, כי אין generation של פרשנות/המלצות.
- יחד עם זאת, **אין עדיין disclaimer מפורש** בממשק המשתמש — זה פער שצריך להיסגר לקראת הרחבת שכבות AI (Layer 2/3).

- frontend:
  - terminal של `npm run dev`
  - Browser DevTools → Console ו-Network (CORS/parse errors)

### Known failure modes (מבוסס על הקוד)
- PDF שלא מכיל טקסט חלוץ:
  - `full_text` עלול להיות ריק → ה-backend מחזיר error envelope עם `detail: "Could not extract text from PDF."`
- קובץ לא-PDF:
  - `_is_pdf_upload(...)` בודק `content_type` או `filename.endswith(".pdf")`
  - במקרה של כשל: error envelope עם `detail: "Invalid file type. PDF required."`
- חוסר תלות Python:
  - אם `PyMuPDF` לא מותקן: import `fitz` ייכשל בעת start.
- API base URL לא מתאים:
  - אם `NEXT_PUBLIC_API_BASE_URL` לא מוגדר והשרת לא ב-`localhost:8000`, ה-UI יחזור ל-`detail: "Invalid response from backend."` (לפי `frontend/src/lib/api.ts`).
- פער מול דרישת 10MB:
  - אין ולידציית size בקוד הנוכחי (רק type PDF). זה “Known gap” מול ה-PRD/הטרנסקריפט.
